# 开发过程与 AI 协作说明

这次项目主要使用 Codex 辅助开发，DeepSeek 则作为产品运行时的模型，负责生成嘉宾、推动讨论和整理观点。我没有直接让 Codex 一次生成整个项目，而是先拆解需求，再按阶段实现和验证。我觉得 AI 辅助开发最重要的不只是生成代码的速度，还要能判断生成的东西是否符合需求、出现问题时能不能找到原因。

**开发过程**

我把开发分成了需求设计、数据模型与 API、前端页面、核心讨论逻辑、端到端测试五个阶段。先整理 PRD、数据结构和验收要求，再建立后端与数据库。前端初期使用明确标记的 Mock 数据验证交互，等后端能力完善后，再接入真实 DeepSeek 调用、动态发言调度和 SSE 实时事件。

每次交给 Codex 的任务都有相对明确的范围。例如开发前端时不允许提前改动讨论引擎，接入模型时尽量复用已有页面，修复问题时先检查相关调用链而不是大范围重构。我会结合 Codex 的实现结果、测试报告和实际网页表现，决定是否需要继续修改。开发中的关键步骤也通过 Git Commit 留下了记录。

**遇到的问题与处理**

开发过程中遇到了几个比较典型的问题。

一是同一事务连续保存事件时出现序号冲突。检查后发现，未 flush 的事件没有参与下一序号计算，修改事务处理后，事件顺序和 SSE 补读测试恢复正常。

二是讨论预算控制不准确。原本要求最多 18 条公开发言，测试时却出现了 19 条。原因是没有给主持人总结预留预算，修正后重新验证了发言数量边界。

三是我在最后亲自通过网页运行真实讨论时，发现右侧两条分歧其实表达的是同一个意思，只是措辞不同。原实现主要依赖文本完全相等匹配，无法识别这种重复。后来让 Codex 先补充失败复现测试，再利用已有洞见 ID 和语义维度进行更新与归并，同时校验证据关系，避免把两个真正不同的观点错误合并。

**测试与验收**

测试没有只看程序能不能启动。后端使用 pytest 和 Fake LLM 验证数据约束、编排与隔离；前端使用 Vitest 和 Playwright 检查交互与完整流程。另外还使用真实 DeepSeek 完成了四名专家参与、18 条公开消息的讨论，并记录了模型调用延迟和实际问题。

最后我又亲自在浏览器中完成了一场真实讨论，检查嘉宾生成、发言互动、共识分歧、主持总结和刷新后的历史恢复。实际使用中发现的问题，也成为最后一轮修改的依据。

**我的理解**

这个项目让我感兴趣的不只是让几个 AI 分别扮演专家，而是让不同专业背景的观点真正产生交锋。有些问题我自己也没有明确答案，如果只问一个 AI，得到的可能是一套比较完整但单一的分析；而不同立场互相追问、反驳时，往往能带出之前没有考虑到的角度。

所以我觉得圆桌讨论的价值不只是生成更多内容，而是让这些观点之间产生联系，同时把真正形成的共识与分歧整理清楚。这也是为什么我认为最后发现的重复洞见值得修复：系统不仅要把讨论呈现出来，还应该尽量准确地保留讨论中有价值的差异。
