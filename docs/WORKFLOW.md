# 开发工作流与 AI 协作记录

这次项目用 Codex 协助开发，用 DeepSeek 作为产品运行时的业务模型。两者分工不同：Codex 负责把需求转成代码、测试、文档并执行检查；DeepSeek 只在用户发起真实讨论时，由后端调用来生成嘉宾、发言、洞见和总结。开发记录以真实 Git 提交、测试命令和实际结果为准，没有使用 Claude Code，也没有把 Fake LLM 结果写成真实模型结果。

我把作业拆为四个可验收的阶段。阶段 0 先写 PRD、架构、验收条件和计划，锁定 2–6 名专家、默认四名、讨论预算与 Mock/真实边界。阶段 1 用 Schema 和 API 契约建立 SQLite 表、外键、生命周期、种子数据及后端测试。阶段 2 根据 API 开发中文大厅、阵容确认和三栏演播厅；后端尚无调度能力时，Mock 演示单独标识、单独存放。阶段 3 再接 DeepSeek、动态调度、SSE、洞见证据和总结。阶段 4 才用真实 Chromium 浏览器串起创建、确认、讨论、停止、刷新、多讨论隔离，并整理交付材料。这种先定事实和边界、后迭代实现的顺序，减少了“页面看起来有功能，实际没有落库”的风险。

每一阶段都限定 Codex 的修改范围：先读仓库已有文档和真实 API，禁止重做已完成的页面，模型密钥始终留在后端；阶段 2 不提前写 AI 引擎，阶段 3 不做无关 UI 重构，阶段 4 优先 E2E 和缺陷修复。关键行为不仅让 AI 生成代码，还用不同层级验证：Pydantic/数据库约束验证输入与隔离，pytest 用 Fake LLM 验证编排和预算，Vitest 验证前端状态，Playwright 在真实浏览器经 Vite 代理请求 FastAPI 并接收 SSE，最后用独立临时数据库做少量 DeepSeek 短讨论。测试脚本不会触碰开发运行数据库；真实模型失败不会自动退回 Mock。

真实遇到的问题比抽象的“AI 偶尔出错”更具体。阶段 1 初始化时 SQLite 父目录不存在，首次测试无法打开数据库；定位到连接创建前的路径准备，补齐目录后重跑，五套样例和 CRUD 测试通过。阶段 3 同一事务连续写事件时，未 flush 的事件不参与下一序号计算，触发唯一约束冲突；改成取最大序号前 flush，事件顺序和 SSE 补读测试通过。阶段 4 的预算边界测试发现默认 18 条会写出 19 条：循环没有为主持总结扣除一条。修正为 `budget - 1` 后，18/24 两个边界均通过。真实 DeepSeek 四专家首测在两条发言后因结构化输出校验失败；检查模型草稿解析与公开文本压缩的顺序后，放宽草稿文本长度、保留最终 160 字约束，复测完成 6 条公开消息、4 条洞见和总结。浏览器截图还发现完成态误报 SSE 重连，因此终态不再订阅实时流，E2E 加入了无重连提示断言。

我理解的工程化 AI 开发不是一次提示词产出所有文件，而是让每一步可定位、可回退、可复现：需求有验收编号，数据有约束，接口有契约，UI 状态有真实来源，模型输出有验证和失败路径，修复有先失败后通过的证据。仍应承认边界：Fake LLM 不能证明真实模型每次都给出高质量讨论；本次真实模型只完成低预算短讨论，长时 18–24 条真实讨论仍需交付前按成本决定是否人工抽检。

最终提交前又进行了一轮原始要求反向追踪。Codex 先核对实现而非沿用阶段总结，确认了提前结束可能漏掉专家、状态事件过快、预设阵容模板化、状态卡表现不足及架构文档偏离代码等问题，再以小范围校验、事件间隔、样例内容和展示样式修复。扩展 Fake LLM 与浏览器回归通过；一次真实 DeepSeek 默认预算运行在 234.5 秒后仍未结束，因此报告保留为部分成功，不用 Fake 结果替代，也没有再次消耗额度掩盖失败。
