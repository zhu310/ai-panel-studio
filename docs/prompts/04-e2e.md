## 二、任务 A：建立真实浏览器 E2E 测试

优先使用 Playwright。

先检查当前 Node 18、Vite 和测试工具链，选择兼容且稳定的 Playwright 版本。

如果环境允许，安装必要的浏览器测试依赖，并创建可重复执行的 E2E 测试。

测试环境必须：

- 使用独立的临时 SQLite 数据库。
- 不污染开发数据库。
- 支持启动和停止测试服务。
- 对需要稳定验证的模型调用使用 Fake LLM。
- 测试结束清理临时资源。
- 不使用固定延时来假装等待流程完成。
- 不通过直接篡改前端状态来绕过真实用户操作。

### 必须验证的业务流程

流程 1：新建讨论

用户打开首页 → 输入话题 → 默认四名专家 → 创建讨论成功 → 进入阵容流程。

流程 2：AI 嘉宾阵容

系统生成主持人与专家 → 用户查看不同立场 → 确认阵容 → 进入演播厅。

验证：

- 嘉宾数量正确。
- 主持人独立于专家。
- Title、背景、立场、颜色正确展示。
- 阵容数据真实来自后端。
- 不能重复确认产生重复记录。

流程 3：完整讨论

用户点击开始 → 主持人开场 → 专家根据上下文参与 → 实时 Transcript → 共识分歧更新 → 主持总结 → 讨论完成。

必须验证：

- 后端真实执行讨论流程。
- SSE 事件实际到达前端。
- 当前专家状态与事件一致。
- 发言一至两句，最多 160 字。
- 内部举手等事件不会被当作 Transcript 消息。
- 共识和分歧不是预先展示的 Mock 结果。
- 讨论完成后展示自然语言总结，而不是 JSON。
- 发言、洞见、事件、总结均可持久化。

流程 4：停止与刷新

- 讨论运行时可以停止。
- 停止后不能继续新增公开发言。
- 刷新页面可以恢复已保存的记录。
- 已完成讨论不会被错误显示为正在运行。
- 页面切换不导致错误订阅或状态污染。

流程 5：多讨论隔离

至少创建 A、B 两个讨论，验证：

- A、B 有不同的话题和嘉宾。
- Transcript 不串线。
- SSE 不串线。
- 共识与分歧不串线。
- 停止 A 不影响 B。
- A、B 的状态持久化独立。

流程 6：异常与边界

- 空话题。
- 专家人数超限。
- API 不可用。
- LLM 调用失败。
- 非法 LLM JSON。
- SSE 中断与重连。
- 重复点击开始或停止。
- 浏览器刷新与重复进入同一讨论。

没有必要为每种异常创建完整浏览器测试；适合接口或单元测试的场景可以使用相应测试层验证。

## 三、任务 B：讨论质量专项验收

不能只验证“生成了若干句话”。

请对讨论质量进行可检查的验证。

### 动态性

检查真实编排是否依赖：

- 话题。
- 专家身份和立场。
- 最近发言。
- 观点冲突。
- 已发言次数。
- 剩余讨论预算。

重点确认：

- 没有固定轮询。
- 存在合理的观点回应、补充或反驳。
- 主持人能够根据讨论进展追问。
- 发言者的选择与上下文存在合理关联。

不要用随机发言顺序作为动态性的唯一证明。

### 共识和分歧

验证：

- 讨论开始前真实模式的洞见为空。
- 讨论中逐渐产生或更新洞见。
- 洞见有真实发言作为依据。
- 证据不能引用其他 Discussion。
- 观点未达成共识时不能被强行描述为共识。
- 不出现大量重复洞见。

### 发言预算

验证：

- 默认预算约 18 条。
- 不超过 24 条上限。
- 允许合理提前结束。
- 不发生无限循环。
- 用户主动停止能够生效。

使用 Fake LLM 覆盖完整预算及边界。

### 真实 DeepSeek 检验

此前已完成三位参与者、五条发言的真实烟雾测试。

如果环境允许，本轮增加一次默认四名专家的真实讨论测试，可以采用较低的公开发言预算，以控制成本。

至少核实：

- 模型正确返回主持人与四名专家。
- 讨论具有上下文关联。
- 能发生有效的观点补充或反驳。
- 真实模式产生洞见和总结。
- 前端能够正确显示真实结果。

不要为了测试数量反复调用真实模型。

完整 18–24 条预算可以主要使用 Fake LLM 验证边界，真实模型长讨论作为可选的人工验收项，并明确说明未覆盖范围。

如果真实调用失败，不允许自动改用 Mock 并声明通过。
