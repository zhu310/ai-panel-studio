## 三、任务 A：完善讨论生命周期和 API

首先检查现有 Discussion、Participant、Message、DiscussionEvent 和 Insight 数据模型。

在尽量复用现有结构的基础上，完成真正的讨论生命周期。

建议流程：

draft → roster_ready → running → completed

允许：

- draft / roster_ready 阶段失败后合理重试。
- running → stopped。
- 发生不可恢复错误后进入 failed。

需要支持：

1. 为指定讨论生成嘉宾阵容。
2. 获取嘉宾阵容。
3. 用户确认嘉宾阵容。
4. 启动讨论。
5. 获取讨论当前运行状态。
6. 停止讨论。
7. 获取已经保存的 Transcript、共识、分歧和最终总结。
8. 获取实时 SSE 事件流。

具体 API 路径按当前 `/api/v1/discussions` 风格设计，并更新 OpenAPI 文档。

要求：

- 同一个讨论不能重复启动多个并行任务。
- 已完成或已停止的讨论不能误启动。
- 重复停止应安全处理。
- 不存在的讨论返回正确错误。
- 状态变更必须持久化。
- 不同讨论的状态完全隔离。

如果需要扩展数据库字段，先确认现有 SQLite 数据不会因为 `create_all` 无法更新旧表而出现问题。

优先复用当前 Schema。确有变更时提供可执行、可复现的迁移方式，不允许直接删除用户现有数据库。

## 四、任务 B：真正的 AI 嘉宾生成

实现后端通过 DeepSeek 根据用户输入话题生成：

- 1 名主持人。
- N 名专家，N 为 2–6，默认 4。
- 每人的姓名。
- 职业或 Title。
- 专业背景。
- 讨论立场。
- 专属颜色。

核心要求：

1. 专家背景与话题相关。
2. 专家之间存在有意义的观点差异。
3. 主持人与专家身份清晰。
4. 生成结果符合 Pydantic Schema。
5. 严格验证专家数量。
6. 模型输出格式不正确时最多纠正重试一次。
7. 仍然失败时返回清晰错误，不得返回伪造成功。
8. 生成阵容必须持久化到指定 Discussion。
9. 用户确认后，才允许进入真实讨论。
10. 预设样例嘉宾仍可正常使用，不要破坏已有 Seed 数据。

必须避免用户重复点击导致多次覆盖或产生重复嘉宾。

为此设计合理的幂等性或状态约束。

## 五、任务 C：实现真正的动态讨论引擎（最高优先级）

这是本次开发的重点。

请设计一个轻量但真实有效的讨论编排器。

### 1. 不允许固定轮询

禁止以下实现：

主持人 → 专家 A → 专家 B → 专家 C → 专家 D → 主持人，不断重复。

应根据：

- 当前讨论主题。
- 当前 Transcript。
- 专家各自立场。
- 已经出现的核心观点。
- 其他专家的反驳或提问。
- 某个观点是否需要进一步澄清。
- 专家近期发言频率。
- 当前剩余讨论预算。

动态选择下一步动作和发言者。

可以采用“LLM 提议下一行动 + 程序约束与校验”的编排方式，避免纯随机调度或复杂多 Agent 基础设施。

主持人负责整体节奏，但专家应能体现主动参与。

### 2. 支持真实互动行为

至少支持：

- 主持人提出问题。
- 专家回应问题。
- 专家主动补充。
- 专家反驳已有观点。
- 专家提出追问。
- 举手或申请发言。
- 合理的插话或优先回应。
- 主持人总结某段争论并推进议题。

这些行为应该由真实讨论上下文或实际调度决策驱动，不能通过随机定时器伪造行为。

可以用结构化内部 Action 表达这些决策，但不要直接把内部 JSON 展示给用户。

### 3. 发言质量

要求：

- 每次公开发言控制在一至两句自然语言。
- 内容需要与前面的发言有关联。
- 不允许多个专家不断重复相同观点。
- 不允许专家长期脱离自己的专业背景和基本立场。
- 允许合理观点修正，但必须有讨论依据。
- 主持人不能完全代替专家进行讨论。
- 输出为自然中文。
- 不展示 chain-of-thought 或模型内部推理。

重点是模拟真正的专家观点碰撞，而不是简单生成多个人的独立回答。

### 4. 控制讨论长度和成本

采用当前约定：

- 默认约 18 条公开发言。
- 最多 24 条。
- 允许根据讨论进展提前结束。
- 用户可主动停止。
- 讨论预算不等于固定轮询。

避免每次发言触发大量没有必要的 LLM 调用。

优先采用精简的结构化调度和必要的模型调用，降低整体延迟和 Token 消耗。

保留清晰的终止条件，防止无限循环。

开发烟雾测试允许使用独立的低预算，例如 4 条发言，但正式默认配置仍遵守上述要求。

## 六、任务 D：实时共识与分歧提炼

讨论进行过程中，系统要能够持续更新：

- 当前共识。
- 关键分歧。
- 共识或分歧涉及的专家观点。
- 对应的真实 Transcript 证据。

要求：

1. 不能仅在讨论结束时一次性生成。
2. 至少在关键讨论节点更新。
3. 不需要每出现一句话就调用一次 LLM。
4. 应对已有 Insight 进行合并、更新或保留，而不是无限重复追加。
5. 不允许凭空编造尚未出现的观点。
6. 能够通过已有 `insight_evidence` 机制关联真实 Message。
7. 严格验证证据 Message 属于当前 Discussion。
8. 共识与分歧必须持久化。
9. 前端实时展示更新内容。

建议复用现有消息结构和证据关联设计，不要新建一套平行数据系统。

## 七、任务 E：SSE 实时事件与运行隔离

必须真正实现后端 SSE，不允许只靠前端定时器模拟讨论。

建议定义统一的事件类型，例如：

- discussion.status
- participant.status
- participant.hand_raised
- message.created
- insights.updated
- discussion.summary
- discussion.error

实际事件类型可根据业务调整。

要求：

1. 每个事件关联 discussion_id。
2. 同场事件有明确递增顺序。
3. Transcript 发言和内部状态事件分离。
4. 真实后端事件驱动前端专家状态变化。
5. 共识和分歧通过事件更新。
6. 事件先持久化，再向订阅客户端发送。
7. 支持 SSE 断线后基于事件序号补读。
8. 重复事件不会使前端产生重复发言。
9. 用户停止后不能继续写入新的 AI 发言。
10. 某场讨论失败不能导致其他讨论一起终止。

### 多讨论并发

支持至少两个不同 Discussion 同时运行。

要求：

- 每场讨论拥有独立的运行任务。
- 各自维护上下文和消息。
- SSE 订阅按 discussion_id 隔离。
- 单场讨论同一时间至多存在一个实际执行任务。
- 不允许共享一个未经隔离的全局 Transcript。
- 异步调用不能长时间阻塞 FastAPI 的其他请求。
- 不应在等待远程 LLM 响应期间长期持有 SQLite 写事务。
- 合理处理 SQLite 并发写入、超时与事务错误。

可以使用单进程内的轻量任务管理方案。

不要求引入 Redis、Celery 或微服务。

但必须明确：进程意外重启后，当前版本如何处理遗留 running 状态。若不支持自动恢复执行，应在重启时明确标记中断并保留历史数据，不允许假装仍在运行。

## 实际设计与实施

- 复用原 SQLite 表；新增 CONFIRMED 状态值，不更改既有表结构。最终总结存为主持人发言和 discussion.summary 事件。
- 后端统一从 .env 读取模型地址、名称与密钥；OpenAI-Compatible JSON 模式，结构化校验失败最多一次纠正重试。模型请求期间不持有 SQLite 写事务。
- 编排器依据嘉宾立场、最近八条发言、发言次数和剩余预算，请模型选择下一行动；程序校验身份、长度、重复和结束条件。公开发言使用中文句界收束到两句、160 字以内。
- 事件先写 SQLite 再由 SSE 按 discussion_id 与递增 sequence 补发；前端按事件序号和消息 ID 去重。进程重启将遗留 running 标为 failed，保留记录。
- 前端保留阶段 2 Mock 演示入口。真实模式从后端生成嘉宾、确认、启动、停止，洞见初始为空，SSE 驱动专家卡、发言、洞见与总结。

## 真实问题与修复

1. 首次低预算实测：真实嘉宾生成成功，短讨论在首轮前失败；后续定位为模型公开发言超过 160 字。增加一次语义纠正与保守中文句界收束，保持模型原意并执行长度上限。
2. 事件序号测试发现同一事务内未 flush 的事件未计入 max(sequence)，导致 UNIQUE 冲突；改为每次分配序号前 flush。
3. 确认接口返回已提交并脱离 Session 的 ORM 对象，导致响应序列化失败；改为事务内构建 Pydantic 响应。
4. Windows 临时 SQLite 文件被连接池占用，烟雾脚本在清理时曾报权限错误；脚本结束时释放连接池并容忍 Windows 清理竞争。
