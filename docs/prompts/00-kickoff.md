## 二、完整业务背景

这是一个面向知识工作者、研究人员、产品决策者和教育内容创作者的 AI 圆桌讨论 Web App。

用户输入一个讨论话题，并指定参与讨论的专家人数，默认四名。

系统通过大模型动态生成一名主持人和若干专家嘉宾。

每位专家具有独立的身份，包括姓名、职业或 Title、专业背景、讨论立场、专属颜色等。

用户确认嘉宾阵容后，进入 AI 圆桌演播厅。

系统由 AI 驱动一场实时推进的讨论，主持人负责引导，专家围绕议题自主发言、补充、反驳、提出问题，并在讨论过程中逐步形成共识与分歧。

讨论结束后，主持人生成自然语言总结。

产品核心价值不是让几个 AI 按固定顺序轮流回答，而是模拟具有观点碰撞、上下文关联和动态互动的真实专家讨论。

## 三、功能需求

### 1. 首页与讨论管理

- 显示所有正在进行的讨论。
- 支持创建新讨论。
- 支持进入已有讨论并查看其当前进展。
- 支持不同讨论同时运行。
- 不同讨论的上下文、运行状态、事件、发言记录、共识和分歧必须隔离。

### 2. 嘉宾生成

用户输入：

- 讨论话题
- 专家人数，默认四人

系统调用大模型生成：

- 一名主持人
- 对应数量的专家嘉宾
- 姓名
- 职业、Title
- 专业背景
- 讨论立场
- 专属视觉颜色

用户确认嘉宾阵容后才能进入演播厅。

嘉宾应具有真实的观点差异，不能只生成观点完全相同的角色。

### 3. AI 圆桌演播厅

主持人负责：

- 开场
- 引导话题
- 提问
- 根据当前讨论内容进行串联
- 推动争议进一步深入
- 结束时进行总结

专家负责：

- 基于自身立场参与讨论
- 根据讨论上下文自主决定是否发言
- 举手申请发言
- 抢答或插话
- 补充其他专家观点
- 反驳其他专家观点
- 根据讨论进展调整自己的表达

要求：

- 单次发言控制在一至两句自然语言。
- 不能机械地按照固定顺序轮流发言。
- 必须能体现观点之间的关联和交锋。
- 主持人和专家的行为要符合各自的身份。
- 讨论过程必须具有实时推进的视觉反馈。

### 4. 专家状态小窗

每名专家都有独立的状态展示区域。

需要显示：

- 待机
- 准备发言
- 发言中
- 当前关注点或公开的观点摘要

不得暴露真实的隐藏 chain-of-thought。

专家状态必须与真实执行过程对应，不能只是前端随机切换动画。

### 5. 实时共识与分歧

讨论进行过程中：

- 持续从实际发言内容中提炼共识。
- 持续发现和更新关键分歧。
- 在页面上实时更新共识、分歧区域。
- 不能等讨论全部完成后才一次性生成。
- 共识和分歧必须能够从讨论内容中找到依据，避免编造。

### 6. 实时 Transcript

展示完整的发言记录：

- 发言人姓名
- 职业或 Title
- 与发言人对应的颜色
- 发言文本
- 时间或顺序信息

不显示内部的举手、抢答等事件作为 Transcript 发言记录。

内部事件可以用于驱动前端状态，但应与面向用户展示的发言内容分开。

### 7. 讨论总结

讨论结束后：

- 主持人通过自然语言总结。
- 总结应覆盖关键观点、共识与分歧。
- 不允许将原始 JSON 直接显示在用户页面。

本项目是具有时间约束的 MVP，避免微服务、过度抽象、无关功能和非必要技术依赖。

## 五、核心技术问题（阶段 0 必须提前考虑）

### 1. 如何让讨论真正动态进行？

请重点分析：

- 主持人和专家之间如何调度。
- 如何根据已有 Transcript 决定下一位发言者。
- 如何支持专家补充、反驳、申请发言等行为。
- 如何避免简单的固定轮询。
- 如何在动态互动与流程可控之间取得平衡。
- 如何控制大模型输出长度、结构合法性及讨论终止条件。

本阶段不实现具体算法，只需要提出可行方案。

### 2. 如何设计系统数据结构？

需要考虑的业务实体至少包括：

- Discussion
- Participant / Guest
- Transcript / Message
- Discussion Event
- Consensus
- Disagreement

请分析各实体的职责、生命周期和关系。

字段设计应由实际业务需求推导，避免为了实现当前几个案例而堆积特殊字段。

### 3. 如何处理实时事件？

重点考虑：

- SSE 的事件模型。
- 后端业务状态如何传递到前端。
- 实时专家状态和实时发言如何同步。
- 断线重连后的状态恢复。
- 不同讨论如何通过 Discussion ID 隔离。
- 事件持久化与 Transcript 持久化的区别。

### 4. 如何保证 AI 输出可用？

重点考虑：

- 嘉宾生成的结构化输出约束。
- 发言内容长度控制。
- 发言角色的身份一致性。
- 共识与分歧的依据。
- 大模型输出不符合 Schema 时如何处理。
- API 超时、调用失败及非法输出的处理方式。

不能把“大模型应该会正确执行”当作测试通过的依据。

### 5. 如何保证多讨论隔离？

至少分析：

- 数据库隔离
- 讨论上下文隔离
- 事件流隔离
- LLM 任务状态隔离
- 前端状态隔离

不需要设计复杂的分布式架构，但必须避免单个全局变量管理所有讨论状态。
