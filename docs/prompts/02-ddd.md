> ## 二、必须完成的页面
>
> ### 页面 A：首页 / 讨论大厅
>
> 要求：
>
> 1. 使用中文界面。
> 2. 页面清晰展示产品名称、产品说明和创建讨论入口。
> 3. 展示已有讨论列表、讨论状态、话题、专家人数及时间。
> 4. 支持创建新讨论：输入话题，选择专家人数（2–6，默认 4）。
> 5. 对接现有 `POST /api/v1/discussions` 和 `GET /api/v1/discussions`。
> 6. 支持进入已有讨论的详情页面。
> 7. 完成加载状态、空列表状态、接口错误与重试交互。
> 8. 讨论列表真实反映后端数据，不使用伪造状态冒充运行中的讨论。
>
> ### 页面 B：AI 嘉宾阵容确认
>
> 要求：
>
> 1. 展示讨论话题。
> 2. 显示一名主持人和指定数量的专家。
> 3. 每位参与者展示姓名、职业/Title、专业背景、立场及专属颜色。
> 4. 专家之间必须有清晰的视觉区分。
> 5. 提供确认阵容并进入演播厅的操作入口。
> 6. 页面体现自然、正式的产品视觉风格。
>
> 注意：阶段 1 尚无真实 AI 嘉宾生成或阵容确认 API。
>
> 因此，请在明确标注的 Mock 演示模式中完整展示阵容确认流程。
>
> 真实 API 模式中可以展示已有样例的嘉宾数据；对于尚未生成嘉宾的新讨论，明确显示“等待生成嘉宾阵容”，不能伪装成已经完成 AI 生成或持久化确认。
>
> 后续阶段 3 再接入真实生成和确认接口。
>
> ### 页面 C：AI 圆桌演播厅（本阶段重点）
>
> 参考专业线上讨论、圆桌会议及 AI Agent 运行控制台的布局设计。
>
> 桌面端建议采用：
>
> - 顶部：讨论标题、运行状态、参与者数量和操作入口。
> - 左侧：主持人与专家区域。
> - 中间：实时讨论 Transcript 主区域。
> - 右侧：共识与分歧面板。
> - 合理位置展示讨论进度、当前发言者、时间等辅助信息。
>
> 主持人要有独立、清晰的视觉身份。
>
> 每位专家使用独立的状态卡片，包含：
>
> - 姓名
> - Title
> - 专属颜色
> - 当前状态（待机、准备发言、发言中）
> - 当前关注点或公开观点摘要
>
> 不得将隐藏的模型推理过程当作专家思考内容展示。
>
> Transcript 要有明显的发言人区分、合理的阅读宽度、良好的文本排版。
>
> 共识与分歧区域必须分开展示，并支持多条记录与更新状态。
>
> 讨论完成后，展示主持人自然语言总结。
>
> ## 三、视觉与交互标准
>
> 这次作业特别考察 UI 是否具有真实演播厅的沉浸感，因此不要做成普通的聊天机器人列表或套用默认管理后台模板。
>
> 设计要求：
>
> 1. 现代、专业、有科技感，但不要使用过多复杂动画。
> 2. 中文字体、行高、颜色和信息层级清晰。
> 3. 主持人与专家有统一但可区分的视觉体系。
> 4. 发言中的专家需要有明显但不过度的高亮。
> 5. 共识与分歧有清晰的信息组织方式。
> 6. 空数据、加载、错误、等待等状态均有可理解的反馈。
> 7. 桌面端尽量使用视口高度内的固定应用布局。
> 8. 不依赖整个页面滚动；Transcript、专家列表及洞见区域独立滚动。
> 9. 窄屏时允许重新布局或切换面板，不能简单压缩到文字重叠。
> 10. 超宽屏需要合理限制文本行宽，避免 Transcript 横向铺满屏幕。
> 11. 避免内容遮挡、横向溢出、按钮不可点击和滚动失效。
> 12. 不引入重型 UI 框架，除非能明显节约开发时间。
>
> 请自主完成合理的视觉设计，不必等待我指定每一种颜色或样式。
>
> ## 四、前端状态与 Mock 设计
>
> 这一部分非常重要。
>
> 阶段 2 尚未实现真正的 AI 讨论引擎，因此需要采用清晰隔离的 Mock 演示机制。
>
> 建议采用：
>
> - API 数据访问层：对接当前真实后端。
> - Mock 数据层：提供演示用嘉宾和讨论事件。
> - UI 状态层：处理当前讨论、参与者状态、Transcript、共识、分歧及总结。
> - 展示组件：尽量不直接依赖数据来源。
>
> 具体结构由你根据项目规模合理决定，不要过度抽象。
>
> ### Mock 模式
>
> 提供一个明确可识别的“演示模式”。
>
> 它应该能演示：
>
> 1. 创建或选择一个模拟讨论。
> 2. 展示嘉宾阵容。
> 3. 确认后进入演播厅。
> 4. 点击开始演示。
> 5. 随着模拟事件逐步更新专家状态。
> 6. 逐条出现 Transcript。
> 7. 讨论进行中更新共识与分歧。
> 8. 讨论结束后展示总结。
> 9. 支持停止演示或返回讨论大厅。
> 10. 切换不同讨论时不发生状态串线。
>
> Mock 发言可以使用事先编写的高质量样例脚本，确保具有观点之间的实际关联、补充和反驳。
>
> 但必须在界面上明确说明这些是演示数据，不是实时 AI 生成。
>
> 不得把 Mock 讨论写入真实后端，冒充真实生成结果。
>
> ### 真实 API 模式
>
> 使用真实 API 完成已经实现的功能：
>
> - 创建讨论
> - 获取讨论列表
> - 获取讨论详情
> - 获取嘉宾列表
> - 获取 Transcript
> - 获取共识与分歧
>
> 对于后端尚未实现的操作，明确显示暂不可用，而不是调用不存在的接口或伪造成功。
>
> 建议把 Mock 模式和真实 API 模式隔离，确保阶段 3 替换数据源后不需要大规模重写展示组件。
